Java supports thread-based multitasking.


Java's primary multitasking/concurrency model is multithreading. Java can also create OS processes, but processes have separate memory spaces and cannot directly share Java objects. Communication between processes must use IPC mechanisms such as streams, sockets, files, etc.

Java's concurrency facilities are primarily thread-based, but Java also provides APIs to create and manage OS processes.

Application of multi-threading in java :- Multithreading allows a server to handle multiple client requests simultaneously.
Technologies like Servlet and JSP use multithreading internally.

Operating System Thread-Schedular
a) pre-emptive
b) time-slice.

Preemptive: If a low-priority thread is running and a high-priority thread arrives, the low-priority thread is immediately stopped, and the high-priority thread gets CPU time.

Time-Slicing: The CPU time is divided into time slices (time quanta). A thread is allowed to run for its allotted time slice, after which the scheduler may switch to another runnable thread.


The JVM specification does not mandate a particular thread-scheduling algorithm. The actual scheduling behavior depends on the JVM implementation and the underlying operating system/platform. Therefore, JVM thread scheduling may use preemptive scheduling and may use time-slicing, depending on the platform and implementation.


Thread scheduling in Java is not guaranteed.
The exact order of execution may vary from OS to OS.

Java threads are scheduled by the operating system scheduler.
Therefore, Java cannot guarantee the exact order of thread execution.
However, Java provides methods like sleep(), wait(), join(), and synchronized keyword which help us control thread behavior, so that multithreaded programs run more or less consistently across different operating systems.

Steps required for a multithreading application

1) Create thread(s)
Create objects of Thread or a subclass/implementation that represents the threads.

2) Define the thread execution body
Define the logic that the thread should execute, typically inside the run() method.

3) Start the thread
java code calls the start() method.

Calling start() causes the JVM to request the underlying operating system to create/start a native thread associated with the Java Thread object. The thread then becomes eligible for execution.


4) Thread scheduler schedules the thread
The thread scheduler decides when and for how long a runnable thread gets CPU time.

When the thread gets CPU time, the JVM executes its run() method.

synchronized keyword
	method :- all the statements are blocked for a particular thread.

	block :- only those statements are blocked for a particular thread which are given inside synchronized block.



what exactly happens when we use synchronized keyword ?

In Java, every object has an intrinsic lock (monitor lock).
When a thread enters a synchronized method or synchronized block, it must first acquire the object's lock.

Only one thread at a time can hold this lock.
Once a thread acquires the lock, it can execute the synchronized code, while other threads trying to access it remain in a blocked state waiting for the lock.

When the thread exits the synchronized method or block, the lock is automatically released, and one of the waiting threads can acquire it.
The selection of the next thread depends on the thread scheduler.

Once a thread acquires the lock on an object, it can access all non-static synchronized methods of that object, while other threads must wait.

Acquiring and Releasing the lock happens automatically.

Actually every object in java has a monitor

That monitor contains:

	Lock (mutex)

	Entry set

	Wait set / wait pool

Even though synchronized method or block is used to avoid "Race Condition", there can be danger of "DeadLock" inside it. 
e.g. if one thread is working inside synchronized block or method and if it gets stuck up !  imagine what will happen ?
neither this thread can complete and release the lock, nor other thread can acquire the lock.

Solution to this is to have a Communication bet'n threads.
i.e. if the thread realizes it can not continue, it should come out of synchronized method or block and release the lock. Now other thread will acquire the lock , execute the code and allow the first thread to resume.

Following are the methods used for communication bet'n threads.

a) wait
	it will make thread release the lock and go to wait pool.
[ Each object in Java has its own monitor, and associated with that monitor is a wait set (wait pool).]

Every Java object has an associated monitor maintained by the JVM.
The monitor contains:

1) Object Lock (Mutex)
2) Entry Set (threads waiting to acquire lock)
3) Wait Set / Wait Pool (threads that called wait())

b) notify
	it will make the thread to move from wait pool to entry set.
c) notifyAll
	it will make all the threads to move from wait pool to entry set.


These methods are defined in "java.lang.Object" class and are final so u can not override them.

These methods must be called from synchronized method or block.
	why it is so?
because wait(),notify() and notifyAll() methods are used to control the lock ( release and acquire the lock) and the concept of lock comes into picture only in case of synchronized method or block.


Execution Flow:

1) Thread tries to enter synchronized block
synchronized(obj)
{
   // critical section
}

If lock is free → thread enters

If lock is busy → thread goes to Entry Set

2) Thread calls wait()
	obj.wait();

Thread:
	releases the lock
	moves to Wait Pool

3) Another thread calls notify()
	obj.notify();

Thread moves from Wait Pool → Entry Set

Then competes for lock again.

We have one more version of "wait" method :
	wait(time in milliseconds)

What happens with wait(time)?

When a thread executes:

	obj.wait(5000);

The following happens:

1) The thread releases the object's lock.
2) It goes to the wait pool (wait set) of that object.
3) The thread stays there either:

until another thread calls notify() / notifyAll(), or until the specified time expires.

4) If the time expires, the thread automatically wakes up.

5) It then moves from the wait pool → entry set (lock seeking state).

6) It must acquire the lock again before continuing execution.

		wait releases the lock on an object , sleep does not.

Since main() is calling "t1.join()" and "t2.join()" , it is added to the end of both t1 and t2. That's why now the statement "Both the threads are over" is getting executed at the end.

User Threads and Daemon Threads

User threads (Non-daemon threads)
Threads that perform the main/application work.
The main thread is a non-daemon thread by default.
Threads created by a non-daemon thread are also non-daemon by default, unless explicitly changed.
The JVM does not terminate while at least one non-daemon thread is still alive.

Daemon Threads

A daemon thread is a background thread that provides services to other threads, typically application/non-daemon threads.

Examples include JVM background threads involved in tasks such as garbage collection.

A daemon thread is automatically terminated when all non-daemon threads have terminated.

The garbage collection thread is indeed an example of a daemon thread. It operates in the background, helping to manage memory without interfering with the execution of user threads, and it automatically terminates when there are no active user threads left.

Daemon Thread: A daemon thread is a background thread that provides services to other threads. The JVM does not wait for daemon threads to finish. When all non-daemon threads have terminated, the JVM terminates, and any remaining daemon threads are stopped.

Example
Thread t = new Thread();
t.setDaemon(true);
t.start();

Here:

t.setDaemon(true)
       ↓
t becomes a daemon thread
       ↓
t.start()
       ↓
t executes in background

Important: setDaemon(true) must be called before start(). Once a thread has been started, its daemon status cannot be changed.

GC threads are also associated with underlying native/OS threads.

The important point is that "GC threads are JVM-created threads", not threads that you create in Java code.

We can visualize it like this:


                    JVM
                     |
        ┌────────────┼─────────────┐
        ↓            ↓             ↓
   Main Thread     t1 Thread     GC Thread
        |             |             |
        ↓             ↓             ↓
   OS Thread       OS Thread     OS Thread
        └────────────┼─────────────┘
                     ↓
               OS Scheduler
                     ↓
                    CPU


So when the JVM starts:

1. The JVM starts the "main thread" → associated with a native/OS thread.
2. When you call `t1.start()`, the JVM creates/starts another native/OS thread for "t1".
3. The JVM's garbage collector starts its "GC worker threads" → these are also typically backed by native/OS threads.
4. The "OS scheduler schedules those native threads" and gives them CPU time.
